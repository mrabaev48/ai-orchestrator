# AI Orchestrator — план дальнейшего развития

> Документ описывает **что строим дальше и почему**. Инженерные решения, контракты и схемы — в [`tech.md`](tech.md).
>
> Дата анализа: 2026-08-31. Базовая ревизия: `df87697` (ветка `fix/git-worktree-race`).

---

## 1. TL;DR

Сегодня репозиторий — это **очень зрелое ядро одного автономного прогона над одним проектом**: policy engine, evidence trail, idempotency/dedup, leases/fencing, repo mutation pipeline, approvals, autonomy L0–L5, SLO/observability. Примерно 23 000 строк продуктового кода, 96 тестовых файлов, 8 версий Postgres-миграций.

Но заявленная продуктовая цель — «оркестратор агентов, которые параллельно работают над разными проектами, с подключаемыми LLM (включая локальные), редактируемыми агентами, MCP, skills и rules» — **сегодня не поддержана архитектурно ни в одном из четырёх измерений**:

| Измерение | Сейчас | Нужно |
|---|---|---|
| Проекты | Один `ProjectState` на процесс, `projectId` берётся из конфига процесса | Проекты — сущность данных, N проектов в одном control plane |
| Параллелизм | Один run за раз на проект, воркер — одиночный poll-цикл, `WORKFLOW_WORKER_COUNT` не используется в рантайме | Очередь + пул воркеров + конкурентность с учётом ресурсов (репозиторий, ветка, лимиты) |
| LLM | Один клиент, один API-ключ, два облачных провайдера, `generateObject` без usage/streaming/tool-calling; `LLM_ROLE_MODELS` влияет только на метрику стоимости | LLM Gateway: N провайдеров и N моделей одновременно, включая локальные; маршрутизация, fallback, реальный usage/cost |
| Агенты и capabilities | 12 захардкоженных ролей в TS-union, промпты — константы, MCP не подключён (SDK в зависимостях, 0 использований), skills/rules отсутствуют | Агент — версионируемые данные (CRUD), capability plane: MCP + skills + rules + tools |

Отсюда стратегия: **не переписывать ядро, а вынести его "вверх" — из однопроектного процесса в многопроектный control plane**, сохранив все инварианты безопасности, которые уже реализованы. Ядро исполнения (`packages/execution`) остаётся почти нетронутым; меняются композиция, состояние, конфигурация и появляются два новых слоя — **LLM Gateway** и **Capability Plane**.

Порядок работ (детали в §7):

```
P0 Мультипроектность + LLM Gateway (в т.ч. локальные модели)
P1 Планировщик и параллельное исполнение
P2 Агенты как данные + MCP/Skills/Rules
P3 UI, approvals-inbox, стоимость и наблюдаемость
P4 Evals, память, контейнерная изоляция, самообучение
```

## 2. Где мы сейчас: карта возможностей

### 2.2 Что блокирует заявленную цель (проверенные факты)

1. **Состояние привязано к одному проекту.** `StateStore.load(): Promise<ProjectState>` — без параметров (`packages/state/src/StateStore.ts`). Проект определяется тем, с каким `projectId` процесс сделал `bootstrap` (`packages/runtime/src/index.ts:57`). Второй проект = второй процесс + второй DSN/схема.
2. **Снимок состояния монолитен.** `save()` пишет весь `ProjectState` целиком с optimistic concurrency, а внутрь состояния входят растущие массивы: `runStepLog`, `artifacts`, `policyDecisions`, `approvals`, `failures`, `decisions`. Стоимость записи растёт линейно с историей прогонов; конкурентная запись двух задач одного проекта гарантированно конфликтует по ревизии.
3. **Один прогон на проект.** `Orchestrator.runCycle()` берёт лизу на ресурс `global-run-cycle`, отскоупленный тенантом/проектом (`packages/execution/src/orchestrator.ts:155`). Параллельные задачи одного проекта невозможны by design.
4. **Воркер не масштабируется.** `apps/worker/src/worker-runner.ts` — один цикл `runCycle` с backoff. Очереди работ нет; `workflow.workerCount` используется только для валидации конфигурации (`packages/shared/src/config/runtime-config.ts:473`).
5. **LLM-подсистема минимальна.** `packages/llm/src/index.ts` (232 строки): единственный метод `generateObject`, провайдеры `openai | anthropic | mock`, один `apiKey` из env. Нет: usage/стоимости из ответа, streaming, нативного tool-calling, ретраев, circuit breaker, локальных провайдеров, нескольких провайдеров одновременно.
6. **Пер-ролевые модели — фикция.** `LLM_ROLE_MODELS` резолвится в `role-runner.ts:224`, но только чтобы проставить тег в метриках и посчитать стоимость; фактический клиент создан один раз с `config.llm.model` (`packages/runtime/src/index.ts:84`). Реального роутинга модели по роли нет.
7. **Токены оцениваются эвристикой.** `estimateObservationTokens` вместо `usage` из ответа провайдера → бюджеты и стоимость систематически неточны.
8. **Действия агента — не диалог, а повторная генерация.** На каждом шаге action-loop весь массив наблюдений сериализуется в один текстовый промпт (`default-roles.ts`, `Observed tool results: ${JSON.stringify(observations)}`). Рост контекста квадратичный, prompt caching невозможен, нативный tool-calling не используется.
9. **Агенты захардкожены.** `AgentRoleName` — закрытый TS-union из 12 значений (`packages/core/src/roles.ts:3`), реализации — классы в `packages/agents/src/default-roles.ts` (1322 строки), регистрация — императивная в `packages/runtime/src/index.ts:119`. Добавить агента = изменить код и пересобрать. Промпты — константы (`packages/prompts/src/prompt-pipeline.ts:16`).
10. **Инструменты закрыты.** `ToolCallName` — union из 13 имён; адаптеры только локальные. **MCP не подключён**: `@modelcontextprotocol/sdk` присутствует в зависимостях корня, использований в коде — ноль.
11. **Skills / rules отсутствуют как продуктовая функция.** Парадоксально: сам репозиторий использует их для собственной разработки (`.agents/skills/*`, `skills-lock.json`, `.codex/subagents/*`, `AGENTS.md`) — то есть готовый работающий образец лежит внутри и не перенесён в продукт.
12. **Конфигурация — процесс-глобальный singleton из env.** `loadRuntimeConfig()` читает `process.env`; per-project и per-agent настройки выразить негде. Секреты — один `LLM_API_KEY` на процесс.
13. **API только на чтение.** Dashboard API даёт read-модели и решения по approvals; создать проект, агента, запустить прогон через HTTP нельзя — только CLI на хосте.

### 2.3 Стратегический вывод

Ядро — это **исполнитель одного прогона**. Продукт — это **control plane над множеством исполнителей**. Недостающие 20% (проекты, очередь, LLM gateway, агенты-как-данные, capabilities) и есть весь продукт: они превращают внутренний инструмент в платформу.

## 3. Целевое видение продукта

**AI Orchestrator — self-hosted control plane, который держит парк AI-инженеров, работающих параллельно над несколькими репозиториями, с полным аудитом, управляемой автономией и любым набором LLM, включая полностью локальные.**

Ключевые свойства целевой системы:

1. **Мультипроектность.** Один инстанс ведёт десятки проектов; у каждого — свой репозиторий, политика, набор агентов, бюджет и уровень автономии.
2. **Параллелизм с учётом ресурсов.** Десятки одновременных прогонов; конкуренция ограничивается не глобальной блокировкой, а ресурсными ключами (репозиторий, базовая ветка, внешний сервис).
3. **Любые LLM.** Облачные и локальные провайдеры одновременно; выбор модели — политика, а не переменная окружения; чувствительные репозитории могут быть жёстко закреплены за локальными моделями без сетевого egress.
4. **Агенты как данные.** Агент создаётся, редактируется, версионируется и удаляется через API/UI без пересборки; изменение агента — это версия, привязанная к прогону в evidence.
5. **Capability plane.** MCP-серверы, skills, rules и tools подключаются к агенту декларативно; политика безопасности всегда пересекается с проектной, а не расширяет её.
6. **Человек в цикле по требованию.** Inbox approvals, вмешательство в середине прогона, пауза/резюм, ревью-бандл с диффом и доказательствами.
7. **Экономика прозрачна.** Реальные токены и деньги на прогон/задачу/агента/проект; бюджеты и квоты — принудительные, а не рекомендательные.

### Non-goals (осознанно не делаем)

- Не делаем «универсальный чат-фреймворк агентов» — оркестратор остаётся инженерным, задача-ориентированным.
- Не делаем auto-merge в default-ветку без quality gates и approvals (закреплено в `docs/autonomous/spec.md`).
- Не делаем SaaS-мультиарендность с общим доверием (изоляция уровня «наш инстанс = наши тенанты»); внешний SaaS — отдельный продуктовый трек.
- Не даём агентам менять собственную policy без governance-процесса.

## 4. Функциональные направления

Каждое направление: зачем, что входит, критерий готовности.

### F1. Мультипроектный control plane

**Зачем.** Без этого нет ни параллельной работы над разными проектами, ни UI, ни экономики.

**Что входит**
- `Tenant` / `Project` / `Repository` как first-class сущности с CRUD.
- Скоупированное состояние: любой доступ к состоянию идёт по `(tenantId, projectId)`.
- Per-project конфигурация (политики, бюджеты, автономия, набор агентов) поверх дефолтов инстанса.
- Регистрация репозитория: URL, креды, базовая ветка, паттерны защищённых путей, команды верификации.
- Разделение снимка состояния и «журналов» (шаги, артефакты, решения) на отдельные таблицы.

**Готово, когда:** один процесс обслуживает ≥10 проектов; `bootstrap`/`run-cycle` вызываются с явным `projectId`; API отдаёт список проектов и их состояние; тест «два проекта, независимые прогоны, состояния не пересекаются» зелёный.

### F2. Планировщик и параллельное исполнение

**Зачем.** Ядро продуктовой ценности — «агенты работают параллельно».

**Что входит**
- Durable-очередь работ (`run_queue`) в Postgres: `SELECT … FOR UPDATE SKIP LOCKED` + heartbeat-lease (механика лизы уже есть).
- Scheduler: справедливое распределение между проектами (weighted round-robin), приоритеты, backpressure.
- Пул воркеров: несколько воркеров в процессе + несколько процессов; `workerCount` наконец начинает работать.
- **Ресурсные ключи вместо глобальной блокировки**: `repo:<id>:branch:<base>` сериализует только то, что реально конфликтует; чтение/анализ параллелятся свободно.
- Параллелизм внутри проекта: несколько задач одновременно, если они не пересекаются по файлам/модулям (используем `affectedModules` из backlog).
- Merge queue: последовательная интеграция PR от параллельных задач с автоматическим ребейзом и повторной верификацией.

**Готово, когда:** 20 одновременных прогонов по 5 проектам без нарушений инвариантов; chaos-тест с убийством воркера восстанавливает работу без дублей side-effect'ов.

### F3. LLM Gateway: подключение любых моделей, включая локальные

**Зачем.** Прямое требование: несколько LLM от разных провайдеров одновременно + локальные модели.

**Что входит**
- **Провайдер как сущность данных**: `ModelProvider { kind, baseUrl, credentialRef, models[] }`. Несколько записей одного kind (например, два разных Ollama-хоста и Azure OpenAI одновременно).
- **Семейства адаптеров**:
  - нативные: OpenAI Responses, Anthropic Messages, Google Gemini, AWS Bedrock, Azure OpenAI;
  - **OpenAI-compatible generic** — один адаптер закрывает vLLM, LM Studio, llama.cpp server, TGI, OpenRouter, Together, Groq, любой self-hosted шлюз;
  - **Ollama** — нативный (`/api/chat`, `/api/tags` для авто-дискавери моделей, поддержка `format: json`/JSON-schema).
- **Матрица возможностей модели**: structured output (native JSON schema / tool-call emulation / grammar), tool calling, streaming, размер контекста, vision, prompt caching, цена за 1k токенов вход/выход.
- **Политика маршрутизации**: `agent × стадия × класс задачи → упорядоченный список кандидатов` с ограничениями (`local_only`, `max_cost`, `min_context`, `requires_tools`).
- **Fallback и устойчивость**: цепочка кандидатов, circuit breaker на провайдера, ретраи с джиттером, отдельные таймауты соединения/генерации.
- **Реальный учёт**: `usage` из ответа провайдера → токены и деньги; эвристика только как fallback с явным флагом `estimated: true`.
- **Локальный режим**: профиль `offline`, где разрешены только провайдеры с приватным `baseUrl`, а любой egress к публичным API запрещён на уровне политики (важно для закрытых кодовых баз).
- **Хранилище кредов**: per-tenant, зашифрованные, с ротацией; env остаётся только как источник bootstrap-секрета.
- **Health-check и дискавери**: периодический опрос провайдеров, список доступных моделей, деградация в UI вместо падения прогона.

**Готово, когда:** в одном прогоне planner идёт в облачную модель, coder — в локальную через Ollama, reviewer — в третью; при недоступности локального хоста происходит документированный fallback; стоимость прогона в UI совпадает с биллингом провайдера.

### F4. Управление агентами (CRUD, версии, тестирование)

**Зачем.** «Возможность добавлять агентов, изменять и удалять» — прямое требование; сегодня это правка TS-кода.

**Что входит**
- **`AgentDefinition` как декларативный документ** (JSON/YAML + zod-схема): идентификатор, версия, вид роли, промпт-шаблон, выходная JSON-схема, разрешённые инструменты, MCP-серверы, skills, rules, модельный профиль, бюджеты, retry/gates, уровень автономии.
- **CRUD API + CLI + UI**, версионирование: `draft → validated → published → deprecated`. Опубликованная версия иммутабельна; прогон ссылается на конкретную версию (evidence воспроизводим).
- **Валидация при сохранении**: схема, ссылочная целостность (существуют ли skills/MCP/модели), безопасность (не расширяет ли права проекта), dry-run на фикстуре.
- **Песочница агента**: запуск на эталонном репозитории-фикстуре с записью полного трейса; сравнение версий агента по метрикам (успех, стоимость, число вмешательств).
- **Совместимость**: 12 существующих ролей поставляются как seed-определения (`builtin: true`); их поведение не меняется, но они становятся редактируемыми — сначала промпт и модель, затем всё остальное.
- **Шаблоны агентов**: набор готовых («security reviewer», «test writer», «dependency updater», «docs writer», «migration assistant») как быстрый старт.

**Готово, когда:** новый агент создаётся из UI/API за минуты, участвует в прогоне, а в evidence видно, какой версией агента и какой моделью получен каждый шаг.

### F5. Capability plane: MCP, skills, rules, tools

**Зачем.** Требование «подключать MCP, добавлять skills, rules»; это же — способ расширять систему без изменения ядра.

**Что входит**
- **MCP-клиент**: подключение серверов (stdio и streamable HTTP), обнаружение инструментов/ресурсов/промптов, неймспейсинг `mcp:<server>:<tool>`, health-check и таймауты. Каждый MCP-инструмент проходит те же гейты, что и локальный: классификация риска, approvals, dedup, evidence. Реестр MCP-серверов: instance-level и project-level, с явным allow-list на проект.
- **Skills**: директория со `SKILL.md` + ресурсами, прогрессивное раскрытие (в контекст попадает только описание, тело подгружается по требованию), lock-файл с хешами источников — точная копия механики, которая уже используется в этом репозитории (`skills-lock.json`). Скиллы привязываются к агенту или проекту.
- **Rules**: машиночитаемые ограничения со скоупом (`org | project | agent | path-glob`) и приоритетом. Два класса: (а) текстовые — инжектируются в промпт; (б) проверяемые — исполняются policy engine (например, «не трогать `packages/state/src/postgres/migrations.ts` без approval»). Второй класс критичен: правило, которое только «просится» в промпте, — это не гарантия.
- **Tools**: расширяемый реестр вместо закрытого union; локальные адаптеры, MCP-инструменты и HTTP-инструменты живут в одном контракте с общей нормализацией ошибок.
- **Context assembly**: детерминированная сборка контекста из state summary + rules + skills + памяти проекта + наблюдений, с бюджетом токенов и приоритетами вытеснения.

**Готово, когда:** проект подключает внешний MCP-сервер и агент использует его инструмент под approval-гейтом; правило уровня проекта блокирует запрещённую мутацию с внятным сообщением; skill подгружается только при релевантности.

### F6. Человек в цикле и UI

**Зачем.** Автономия без наблюдаемости не продаётся и не эксплуатируется.

**Что входит**
- Web UI: список проектов и прогонов, живой таймлайн шагов (SSE/WebSocket), просмотр диффа, evidence-бандл, стоимость.
- **Approvals inbox** с SLA-эскалацией (движок уже есть: `packages/application/src/approval/*`) + уведомления в Slack/Telegram/email.
- **Вмешательство в середине прогона**: пауза, комментарий-подсказка агенту, отмена задачи, ручное редактирование плана.
- Редакторы: агентов, правил, промптов, политик — с diff-просмотром и историей.
- Onboarding-мастер: подключить репозиторий → выбрать/добавить провайдера модели → собрать команду агентов → первый прогон в режиме `propose-only`.

**Готово, когда:** оператор ведёт 10 проектов из браузера, ни разу не заходя на хост по SSH.

### F7. Governance, стоимость и безопасность

- Бюджеты и квоты: инстанс / тенант / проект / агент / прогон; мягкий порог (алерт) и жёсткий (стоп).
- Дашборд экономики: стоимость на смерженный PR, на задачу, доля вмешательств человека, распределение по моделям.
- Защита от prompt injection: контент репозитория и ответы MCP — данные, а не инструкции; изоляция инструкций, запрет на автоэскалацию прав из содержимого файлов.
- Egress-контроль: allow-list доменов для инструментов и провайдеров; режим «полностью локально».
- Расширение RBAC/ABAC с CLI на HTTP API; сервисные аккаунты и API-ключи.
- Ротация секретов, шифрование кредов, аудит доступа к секретам.

### F8. Интеграции

- **Git-хостинги**: GitHub/GitLab/Bitbucket — реальные PR (сейчас только draft-бандл), статусы, комментарии ревью, реакция на события.
- **Триггеры**: webhook (PR открыт, CI упал, issue помечен лейблом), cron-расписания, ручной запуск, событие из CI.
- **Трекеры**: Jira/Linear/GitHub Issues — импорт задач в backlog и обратная запись статусов (для этого уже есть `IntegrationExportService`).
- **CI**: запуск проверок на стороне CI вместо локальной верификации, приём результатов как evidence.

### F9. Наблюдаемость и качество агентов

- OpenTelemetry-экспорт метрик и трейсов (внутренние стораджи уже пишут метрики/спаны — нужен экспортёр).
- **Evals**: набор эталонных задач на фикстурных репозиториях, регрессионный прогон при изменении промпта/модели/агента; отчёт «версия агента A против B».
- Replay прогона: детерминированное воспроизведение по evidence, включая запись/подмену ответов LLM (record/replay LLM cassettes).
- Кластеризация отказов: автоматическая группировка `FailureRecord` в паттерны и предложение правил.

### F10. Дополнительные фичи, дающие много при малой цене

| Фича | Идея | Ценность |
|---|---|---|
| Планировщик прогонов | Ночной прогон «tech-debt агента» по расписанию | Работа идёт, пока команда спит |
| Память проекта | Долговременные заметки: архитектурные решения, грабли, конвенции; извлекается в контекст по релевантности | Агент перестаёт повторять ошибки |
| Индекс репозитория | Символьный/семантический индекс для точечного контекста вместо «прочитать полрепозитория» | Дешевле и точнее |
| Shadow-режим | Агент работает, но результат только предлагается; сравнение с тем, что сделал человек | Безопасный набор доверия |
| Контейнерная песочница | Прогон в Docker с ограниченной сетью и ресурсами | Возможность работать с недоверенным кодом |
| Дебаты/критик | Второй агент оспаривает решение первого перед дорогими действиями | Меньше ложных «готово» |
| Каталог агентов | Импорт/экспорт определений агентов между инстансами | Обмен практиками между командами |
| Стоимостный роутер | Автовыбор дешёвой модели для рутинных шагов, дорогой — для сложных | Прямая экономия 40–70% |
| Cassette-режим | Записанные ответы LLM для тестов и демо | Быстрые детерминированные e2e |
| Диагностика «почему стоим» | Явный ответ на «почему прогон idle»: нет задач, лок, бюджет, ожидание approval | Снимает главный вопрос эксплуатации |

## 7. Дорожная карта

### P0 — Фундамент: проекты и модели (≈4–6 недель)

**Цель:** один инстанс ведёт несколько проектов; модели подключаются как данные, включая локальные.

1. Доменные сущности `Tenant/Project/Repository` + миграции; `projectId` — явный параметр везде.
2. Разделение состояния: снимок отдельно, журналы отдельно; `StateStore` получает скоуп.
3. `RuntimeConfig` → `InstanceConfig` (env) + `ProjectConfig` (данные) с наследованием и валидацией.
4. Новый пакет `packages/llm` v2: `ModelProvider`, реестр, адаптеры (OpenAI, Anthropic, OpenAI-compatible, Ollama), capability-матрица, usage/cost, ретраи, circuit breaker.
5. Роутинг модели по роли — реальный (устраняем расхождение конфига и поведения).
6. Хранилище кредов провайдеров (шифрование, per-tenant).
7. CLI: `project create/list`, `provider add/test`, `run --project <id>`.

**DoD:** e2e-тест — два проекта, разные провайдеры (один локальный), независимые прогоны, корректная стоимость по каждому.

### P1 — Параллелизм (≈4–6 недель)

1. `run_queue` в Postgres + `SKIP LOCKED` + heartbeat-lease + dead-letter (переиспользуем существующие механизмы).
2. Scheduler с честным распределением и приоритетами; backpressure по бюджету и по числу активных прогонов.
3. Ресурсные ключи блокировок вместо `global-run-cycle`.
4. Пул воркеров: N в процессе × M процессов; graceful shutdown, дренаж лиз.
5. Параллельные задачи внутри проекта по непересекающимся модулям + merge queue.
6. Переход action loop на messages + нативный tool-calling + prompt caching (снимает квадратичный рост).
7. Нагрузочный и chaos-профиль под новую модель конкурентности.

**DoD:** 20 одновременных прогонов, 5 проектов, убийство воркера в середине мутации не приводит к дублирующимся push/PR.

### P2 — Агенты и capabilities (≈5–7 недель)

1. `AgentDefinition` (схема, хранилище, версии, публикация), компиляция определения в исполняемую роль.
2. Seed существующих 12 ролей как builtin-определений; поведенческий паритет подтверждён тестами.
3. CRUD API + CLI + валидация + dry-run на фикстуре.
4. Реестр инструментов вместо union; MCP-клиент (stdio + HTTP), неймспейсы, гейты, evidence.
5. Skills (SKILL.md, lock-файл, прогрессивное раскрытие) и Rules (текстовые + проверяемые).
6. Пайплайн сборки контекста с бюджетом токенов.

**DoD:** пользовательский агент с подключённым MCP-сервером и двумя правилами проходит полный цикл до PR-бандла; попытка выйти за права проекта блокируется.

### P3 — Продукт: API, UI, интеграции (≈6–8 недель)

1. Write-API (проекты, агенты, прогоны, approvals, провайдеры) с RBAC и API-ключами.
2. Web UI: проекты, живой трейс, дифф, approvals inbox, стоимость, редакторы агентов/правил.
3. Реальные PR в GitHub/GitLab; комментарии ревью; статусы.
4. Триггеры: webhooks + расписания.
5. Уведомления и эскалации.

**DoD:** полный путь «подключил репозиторий → собрал агентов → получил PR» без CLI.

### P4 — Зрелость (постоянный трек)

Evals и регрессии агентов, replay с LLM-кассетами, память проекта и индекс репозитория, контейнерная песочница, стоимостный роутер, каталог агентов, автоматическая кластеризация отказов и предложение правил.

## 8. Метрики успеха

**Продуктовые**
- Задач доведено до смерженного PR без вмешательства человека, %.
- Среднее число человеческих вмешательств на задачу (цель: снижение по кварталам).
- Стоимость одного смерженного PR (токены + инфраструктура).
- Время от постановки задачи до готового PR (p50/p90).

**Платформенные**
- Одновременных прогонов на инстанс (цель P1: ≥20).
- Доля прогонов, завершившихся нарушением инвариантов: 0.
- Доля side-effect'ов, защищённых idempotency-ключом: 100% (уже достигнуто, не терять).
- Точность учёта стоимости против биллинга провайдера: ±2%.

**Эксплуатационные**
- MTTR инцидента прогона по одному лишь evidence-трейлу.
- Доля прогонов, для которых полный root-cause восстановим без доступа к хосту: 100%.

## 9. Риски и снятие

| Риск | Проявление | Снятие |
|---|---|---|
| Миграция состояния ломает работающее ядро | Регрессии в инвариантах | Strangler: новый скоупированный store за фасадом старого порта; baseline-invariants тесты как ворота (уже есть `tests/baseline-invariants-regression.test.ts`) |
| Параллелизм даёт гонки на репозитории | Повреждённые worktree, конфликтные push | Ресурсные ключи + существующий мьютекс worktree + merge queue + chaos-тесты |
| Пользовательские агенты повышают себе права | Обход политики | Права агента = пересечение с проектной политикой; агент не может расширять, только сужать |
| MCP-сервер — недоверенный код | Утечка данных, инъекции | Sandbox процесса, allow-list, гейты, вывод MCP — данные, а не инструкции |
| Локальные модели слабее в structured output | Схема не валидируется, прогоны падают | Три стратегии structured output (native schema → tool-call → grammar/repair), автодеградация и метрика по модели |
| Растущая стоимость при параллелизме | Незаметный перерасход | Жёсткие бюджеты на всех уровнях + стоп по порогу + дашборд |
| Разрастание объёма работ | Всё сразу, ничего до конца | Фазы P0…P4 с DoD; в каждой фазе — один вертикальный e2e-сценарий |
